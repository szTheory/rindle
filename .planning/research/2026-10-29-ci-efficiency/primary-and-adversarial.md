Cache allowance is 10 GB per repository; overage billing requires a configured higher limit. A larger runner is a policy/cost experiment, not a free optimization; test actual workloads before considering one. |
| Cancellation and queues | Default concurrency keeps one running and one pending member; a new member replaces the pending one. Current docs support `queue: max`, up to 100 pending, incompatible with `cancel-in-progress: true`. Processing follows waiting arrival, not guaranteed dispatch order. [Concurrency reference](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency). | `cancel-in-progress: false` protects the running producer, not every pending request. Queue size alone cannot prove producer ownership, completeness or freshness. |
| Topology | Jobs run in parallel unless `needs` constrains them. Failed/skipped prerequisites skip dependents unless the conditional explicitly continues them; matrix fail-fast cancels siblings when enabled. [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds). | Flatten only edges carrying no required input, preserve final aggregation, and test every failure/skip/cancel route. `fail-fast: false` buys diagnostics and full-cell evidence at the cost of extra failing-run work. |
| Cache result labels | `cache-hit` means an exact key match. A fallback restore is not an exact hit, and an existing key is immutable. The action supports distinct restore/save operations. [Cache action upstream](https://github.com/actions/cache/blob/main/README.md). | A false hit label can still restore useful bytes; a true hit neither proves validity nor measures time saved. Key policy, compile validation and observed restore/build duration matter. |
| Fork/cache trust | Base caches are readable by fork PRs; secrets never belong in cache paths. PR-written caches are merge-ref scoped and not restorable by base/other PRs. Cache contents are not signed or verified. [Dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). | Preserve fork-safe proof and namespace isolation. A lock hash is an invalidation component, not a signature, authorization boundary or secret-protection mechanism. |
| New cache hardening | June 2026 hardening makes untrusted events in **default-branch scope** read-only; it does not disable ordinary `pull_request` merge-ref cache writes. Denied saves warn and continue. [GitHub announcement](https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers/). | Do not diagnose every fork cache miss as a defect or add a privileged cache-writer workflow. Do not override secure defaults with write-capable cache policy merely to improve hit rate. |
| Artifact integrity | Upload exposes artifact ID/digest and immutable artifacts; matrix uploads need unique names. Compression trades upload CPU for bytes. [Upload action upstream](https://github.com/actions/upload-artifact). Download digest mismatch only produces a warning in GitHub's tutorial. [Artifact verification](https://docs.github.com/en/actions/tutorials/store-and-share-data#validating-artifacts). | Keep the repo's fail-closed producer-sidecar, archive, manifest, run/attempt and transport checks; a green download step is insufficient. No artifact-name-only lookup or overwrite of historical receipt identity. |
| Scheduling and retries | Schedules use default-branch commits, can be delayed/dropped under load, and public schedules disable after 60 inactive days. Reruns retain original event SHA/ref. [Schedule semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [rerun identity](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs). | Preserve true scheduled recovery and distinguish scheduled, manual and rerun evidence. A successful manual run, wall-clock cron tick, or a rerun cannot certify a newer subject or replace an actual schedule obligation. |

The May 2026 [larger queue announcement](https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues/) matters when reading older advice that GitHub cannot queue more than one pending run. It changes available mechanisms, not the repository's accepted policy.

## Decisions, alternatives, smallest changes, and automated acceptance

### 1. Keep current DAG gains; do not equate parallelism with less work

Current [CI topology](https://github.com/szTheory/rindle/blob/b2a60c51687293df5498920cc2bddb4e25349251/.github/workflows/ci.yml) starts Proof after optional dependencies, independently of Quality; final `CI Summary` still includes both. Full main keeps all five consumer profiles and common preflight only in image. No new edge removal is justified solely because waiting time is long.

**Pros:** shorter successful feedback can require no new command, dependency, artifact or permission. Common-preflight deduplication reduces repeated work directly. **Cons:** if Quality fails, overlapping Proof consumes work the old DAG skipped; concurrent cold compilers can contend for caches/runners and delay other jobs. Removing another edge can have no wall-time effect when a different path dominates.

**Smallest next step:** consume the timing agent's existing terminal job/step inventory and compare command-equivalent runs grouped by PR/main, success/failure/cancel, toolchain and cache state. Do not launch benchmark reruns just to manufacture a nicer comparison. If the next dominant wait is an input-free edge, propose one changed `needs` list and preserve the sole `CI Summary` context, workflow/file identity and exact-SHA full-run release gate. A separate setup/fan-out job needs evidence that saved repeated work exceeds its runner setup, artifact I/O and new serial dependency.

**Automated acceptance:** retain `test/install_smoke/ci_lane_split_test.exs` plus CI/Nightly summary behavior harnesses; assert required topology and unchanged command/profile inventory. Inject each required lane's failure, missing, cancellation and impermissible skip and require final red. For any claimed gain, retain raw timestamps, queue spans, completed/canceled work and matched conditions. **Falsifier:** no material critical-path reduction, higher failure-adjusted work without an accepted latency benefit, or any masked gate. Revert only the optimization under test.

An analytical identity, not a result: expected total work depends on passing-run work **and** failing/canceled-run work. Starting job B early can save the dependency wait on success while adding up to B's consumed runtime on an upstream failure. Counting only successful runs hides this cost.

The root team's finite candidate set should use these adversarial tests; its timing/source reports own the numeric estimates:

| Candidate | Scope and tradeoff | Minimum falsifiable acceptance |
|---|---|---|
| Start the full main consumer matrix before Quality if it consumes no Quality outputs | Small scheduling change, potentially material latency benefit; **no green-run runner-minute reduction**. More consumer work runs on Quality failures. Preserve exact-SHA full-run release authority and every profile. | Current-source command/input comparison, modeled complete DAG and hosted terminal observation; an injected Quality failure must keep the final release gate red. Reject if contention moves the critical path or evidence changes. |
| Remove a repeated image/package proof | Real work reduction only if the outputs and environment are equivalent. `MIX_ENV=dev` versus `test`, package bytes, dependency selection and cold generated-consumer boundary may make two similarly named commands different proofs. | Demonstrate equality of actual artifacts/inputs and unchanged failure detection before removing any invocation. Retain the five profile contracts and required dry-run/preflight behavior. A shared name or always-green history is not sufficient. |
| Remove outer retention bootstrap repeated by private qualification | Small bounded candidate; an isolated fresh qualification can intentionally rebuild. Outer compile/setup may also be a prerequisite for admission or archive generation. | Trace actual downstream consumers and configuration before deleting only the redundant outer work. Preserve private-source cleanliness, supported toolchain, cold/native package proof, every gate and cleanup. Reject any replacement with cached authority or shared mutable build outputs. |
| Add periodic progress relay | Operational visibility, not a qualification-speed saving. A separate job can unexpectedly become part of topology-derived all-jobs acceptance, even with job-level `continue-on-error`; a failed job result can still be rejected by the verifier. | Prefer the existing job's bounded step observer with explicitly tolerated **step** failure and an always-written status result, then fixture both normal and failed-observer job states against the real topology/verifier. A green Summary alone is insufficient. No observation can mutate/cancel/retry the producer or leak secrets; lifecycle/signal/cleanup parity must hold. |

Any observer needs its own upper time bound and retained failure status; swallowing its failure without output creates another false-green path. If receipt-control bytes or declared topology change, use the existing compatibility/admission rules and sequence after the owned acceptance unless the owner deliberately selects a new subject and obtains its required evidence.

### 2. Preserve producer ownership; queue expansion is an explicit policy change

Current main CI separates PR-number groups from ref groups. Current [Readiness Retention](https://github.com/szTheory/rindle/blob/b2a60c51687293df5498920cc2bddb4e25349251/.github/workflows/readiness-retention.yml) groups by expected subject and disables running cancellation. This prevents some cross-subject collisions but does not make several pending requests for the same subject durable. A fresh request ID is not by itself proof of exactly-once dispatch or permission to spend a new producer.

**Decision:** keep the owned controller's run/attempt/nonce identity and existing run discovery/retrieval. No cancellation, rerun or dispatch of `40864930767/1` is authorized by this research. Do not add `cancel-in-progress: true` to main, retention, release or the Nightly incident mutator as a cost-saving shortcut.

**Alternatives:** `queue: max` can reduce pending replacement but runs more obsolete work, has a hard bound and cannot guarantee dispatch order. It cannot simply be added to CI while its conditional cancellation can be true. Unique per-request groups avoid coalescing but permit simultaneous expensive producers and overlapping side effects. A custom queue service adds more failure states and dependencies. None is a routine optimization; each changes evidence/recovery semantics and requires a separate owner decision.

**Smallest justified change if collisions are demonstrated:** clarify pending-versus-running behavior in comments/controller diagnosis; then, only if required, change one workflow queue policy with exact ownership rules. **Automated acceptance:** fixture three same-subject requests with one running/two pending; require explicit terminal disposition or authenticated discovery for each, reject wrong attempt/nonce, and prevent an orphan from being relabeled success. Use existing readiness acceptance/retention harnesses, then a separately authorized hosted probe because a YAML fixture cannot prove GitHub's scheduler. **Falsifier:** overlapping side effects, an unobservable consumed request, stale proof promotion, or more work without resolving the observed loss.

### 3. Keep Nightly event persistence and replay; do not replace it with a queue flag

Current [Nightly](https://github.com/szTheory/rindle/blob/b2a60c51687293df5498920cc2bddb4e25349251/.github/workflows/nightly.yml) persists each scheduled strict verdict before the replaceable incident pending slot, then replays events with an authenticated checkpoint. This protects red→green incident history when pending drainers disappear. Moving persistence after the slot, merging Nightly into `CI`, or using a new-ID-only checkpoint can lose failures or a changed attempt of an older run. Release consumers make workflow identity a real boundary.

**Pros:** current mechanism tolerates coalesced drainers and avoids a new state service. **Cons:** it costs artifact/API work and depends on retained replay inputs. **Smallest next step:** keep it, using existing incident fixtures to cover pending replacement, old-ID/new-attempt, missing/expired events, red→green and repeated observations. If measurement identifies remote historical expansion as dominant, optimize the current checkpoint lookup while retaining changed-attempt detection; no unmeasured polling redesign.

**Automated acceptance:** `scripts/ci/test_nightly_incident.sh`, `test_nightly_summary_gate.sh`, and `test_verify_nightly_run.sh` must preserve strict aggregation, authentic scheduled identity, replay closure and no duplicate mutations. Fixture success is regression protection; actual schedule recovery still needs actual event/run evidence. The temporary `27 13 27 10 *` entry is annual until removed, not a one-time timer; remove it only after its already-defined retained historical acceptance condition, as a separately sequenced control change. **Falsifier:** lost incident events, silent expiry, manual-as-scheduled substitution, or release activity caused by Nightly identity changes.

### 4. Retain toolchain/ABI cache boundaries and real process tests

Current [setup action](https://github.com/szTheory/rindle/blob/b2a60c51687293df5498920cc2bddb4e25349251/.github/actions/setup-elixir/action.yml) keys `deps`/`_build` by OS, architecture, resolved OTP/Elixir, MIX_ENV, lock hash and a version buster; optional-dependency proof uses a separate namespace. Fallback spans lock hashes only. This is existing discipline, not proof that every native library/config change is represented. Native runner/image or compile-environment changes may require an explicit buster; do not broaden fallbacks across those dimensions.

Mix 1.17.3 [compile source](https://raw.githubusercontent.com/elixir-lang/elixir/v1.17.3/lib/mix/lib/mix/tasks/compile.ex) describes dependency/up-to-date checks and flags that bypass checks. Keep normal dependency fetch and compile validation after restoration; do not translate `cache-hit == true` into `--no-compile`, `--no-deps-check` or acceptance reuse. [Setup-beam upstream](https://github.com/erlef/setup-beam) distinguishes requested ranges from resolved versions; cold caches after patch resolution changes can be correct.

[Dialyxir](https://dialyxir.hexdocs.pm/readme.html#continuous-integration) recommends PLT caching and rebuilding for changed Erlang/Elixir versions. The repo deliberately proves more: fresh build/analyze, save, delete, exact restore, and independent restored analyze. Keep both; an exact cache hit does not replace either analysis. Do not introduce `--no-check`, `--ignore-exit-status`, cross-input PLT fallback or narrower dependency analysis to hide cost.

The shipped [Mix 1.17.3 test task](https://github.com/elixir-lang/elixir/blob/v1.17.3/lib/mix/lib/mix/tasks/test.ex) explicitly warns that same-VM repetition can retain global state; `--no-start` changes application startup. Thus `mix do`, daemonization, blanket async, or in-memory substitution cannot universally amortize the current subprocess harnesses. Keep the delivered batching confined to pure validator requests with fresh request state plus real CLI/path/signal/deadline/cleanup parity.

**Small safe opportunity only if measured:** eliminate an actual duplicate install inside one pinned runtime context, or add bounded cache restore/fetch/compile timing to the existing summary. Do not share host/container `node_modules`, native `_build`, mutable DB fixtures, global env or package-authority receipts. A new omnibus image/cache hierarchy creates maintenance, trust and invalidation work.

**Automated acceptance:** normal compile/test contracts, cache-key static assertions supplemented by cold/fallback/exact restored execution, actual native/generated-consumer checks, existing Dialyzer mode/failure harness, and fresh-versus-batched verdict/reason/digest plus A→bad-B→A isolation. For issue #42 retain the **exact** seeds `0,17,43,71,101,131,173,211,257,307,353,401,449,503,557,601,653,701,757,809,863,911,967,1013,1061`, one fresh foreground `mix coveralls.multiple --type local --type json --seed SEED --slowest 20` per seed, stop on nonzero, local-only. No repeat-in-one-VM substitute or extra CI coverage loop. **Falsifier:** mismatched bytes/toolchain, restore slower than the saved build, changed failure verdict, leaked process state or reduced qualification breadth.

### 5. Separate disposable diagnostics from retained authority before touching storage

Current CI uses 14-day JUnit/coverage retention in several lanes; browser reports upload on failure, with other reports using action defaults where no per-artifact retention is set. Nightly verdict/checkpoint artifacts retain 14 days; readiness archives, sidecars and redacted failure diagnostics retain 30. These are distinct purposes, not one pool to truncate indiscriminately.

**Decision:** first inventory artifact byte sizes, creation/expiry, purpose, consumers and required replay/retrieval horizon. Billing reduction remains unknown without the owner's actual eligible storage data. For billed storage, estimate byte-hours rather than artifact counts. Logs and job summaries are suitable for a compact timing table; they are not a durable replacement for required receipts.

**Pros of shorter diagnostic retention:** less retained disposable data. **Cons:** lost incident/debug window; shrinking event retention can make replay unverifiable, and shrinking readiness retention can break durable retrieval. Changing compression on an already compressed archive may waste CPU; the current readiness archive already uses compression level 0.

**Smallest implementation if data supports it:** one explicit retention value for a demonstrated oversized, disposable report, with no authority consumer; leave immutable acceptance artifacts alone. **Automated acceptance:** artifact-purpose inventory checked against workflow names/consumers; retention cannot be below the declared recovery horizon; existing retention fixtures must reject missing, expired, ambiguous, foreign, wrong-attempt or digest-mismatched artifacts. Do not treat `download-artifact`'s warning-only validation as this gate. **Falsifier:** any expected recovery loses bytes, or no material eligible storage reduction is demonstrated.

## A lightweight evidence and learning loop using existing primitives

Borrow one mechanism across ecosystems: [SLSA build provenance](https://slsa.dev/spec/v1.2/build-provenance) separates build definition/inputs, invocation details and output subjects. Use that distinction in the existing receipt shape; do not add an attestation dependency or claim a SLSA level. A cache is an input/acceleration mechanism; an invocation is one execution; a verdict is a claim over authenticated bytes and time. They cannot substitute for each other.

For a CI-affecting PR or an actual incident, append one finite evidence record under the existing dated `.planning/research/.../` convention, plus one short decision/lesson entry. Reuse terminal workflow/job/step data already collected by the timing tools, `gh`, Python/jq and existing validators. Never run the active `collect_pr_timing_receipt.sh run/current-run` sampler casually: it is a separately authorized, side-effecting exact-ten acceptance path. Ordinary learning reads completed runs; it does not generate extra coverage, producers or schedules.

Minimum fields: question/change, subject SHA and policy/workflow blob, repo/event/run/attempt, resolved toolchain/runner class, cache exact/fallback/absent/unknown, command inventory, queue/dependency/wall span, summed job seconds including canceled work, outcome/applicability, artifact sizes/expiry when relevant, raw-source links/digests, decision/falsifier, owner and a fixed stop condition. Keep missing fields unknown. A lesson states the observed trigger, consequence, retained guard and when it would be reconsidered; avoid accumulating repetitive narrative.

**Smallest implementation:** a bounded post-run JSON transform and Markdown table beside the existing timing evidence, invoked at CI-change/incident closeout rather than every minute. Reuse the existing artifact-ledger classification if new files become tracked. No new workflow, dashboard server, telemetry SDK, database, queue service or dependency is needed. Do not make an advisory learning table another release gate.

**Automated acceptance if implemented:** fixture malformed/missing timestamps, canceled jobs, partial pagination, duplicate/missing jobs, changed attempt, nonterminal runs, wrong event/SHA and unknown runner billing; require honest failure/unknown values and no savings claim from incomparable data. Assert no extra execution/dispatch commands and finite retained output. Run the automation-first contract after any active planning changes. Existing raw evidence remains immutable; derived tables identify their input digest.

Control observer effects: API collection, debug logging, `--slowest`, runner/cache prewarming and repeated qualification can change the measured workload. Prefer passive terminal metadata, record collection overhead, and distinguish diagnostic commands from normal acceptance. Compare the same event/source/toolchain/command/cache class when possible; otherwise label the result descriptive. A small success-only sample is not causal proof, reliability, p95, CI-16 closure, READY or billing savings.

Stop after the next dominant measured cost has one accepted decision. Reopen only for a material new cost, correctness incident or changed upstream constraint. The already-owned live acceptance and independently required pilot remain separate outcomes; this report adds no work to either execution.
