**1. Expose bounded qualification progress before optimizing the multi-hour path.**

The historical successful producer `40609107572` spent251.45 of 254.6 minutes inside Collect; prerequisites took 148 seconds. Failed producer `40695062822` spent 96.53 minutes in Collect and 149 seconds in prerequisites. This is a different budget from ordinary PR/main CI. Outer-setup caching cannot by itself materially shorten the successful qualification.

`Qualification.command` already records command duration, interval, argv and redacted output in private/portable evidence. `run_reserved` prints `QUALIFY <fixed-id>` before each gate. However `Closure.command` directs the qualification child's combined stdout/stderr into its restricted log and normally prints it only on failure. More `flush=True` in the child alone cannot expose live progress in hosted logs. Async isolation runs 25 fresh sequential coverage processes, stores each iteration's complete output in a temporary file, and its strict receipt has no duration field. A long quiet Collect step is therefore expected with the present plumbing.

| Choice | Decision and decisive tradeoff |
|---|---|
| Keep opaque Collect / dump raw child output | Reject as the eventual observability design: the first hides the stage; the second exposes arbitrary output and workflow-command/secret risks |
| Small explicit public progress protocol + bounded relay | Prefer. Standard Python/Bash only; fewer than 100 ordinary events for 18 gates and 25 seeds, plus a low-frequency bounded heartbeat if required |
| New telemetry service, queue, profiler dependency | Reject for this finite producer |

Smallest implementation: emit a fixed-prefix JSON record at gate start/end and async seed start/end, with only allowlisted gate ID, ordinal, fixed seed/index, monotonic elapsed/duration, integer exit and state. Preserve the existing strict async receipt schema; put timing in a separate progress sidecar, never the authority receipt. Relay only validated progress records through the closure's captured-output boundary while keeping the original restricted capture and bounded child disposal. A polling reader of the captured file is sufficient if it bounds offsets, partial lines, total events and lengths; a dedicated pipe is an alternative with more lifecycle work. Never relay argv, file paths, issue/advisory bodies, env values or raw test tails. A malformed progress record is an observation error, never successful proof. Readiness remains decided by existing receipts, exit codes and complete graph validation.

Adverse acceptance: a secret canary, forged workflow-command line, oversized/partial JSON and unknown gate/seed never reach public output; a dead/timed-out child produces no successful finish;25 valid records cannot rescue missing/failed proof; all owned processes still disappear after signal/deadline. On a short controlled run, public start must arrive before the child finishes, end duration must agree with command evidence within polling tolerance, and event overhead must be measured. Future normal attempts then provide per-gate/per-seed distributions without a new benchmark run. Do not parallelize the25 processes as part of this change: isolated DBs, ports, native runtimes, output trees, services and exact complete aggregation would be a separate, higher-risk contract design.

**4. Make timing observation advisory in every authority, not just in CI Summary.**

`ci-observability` is labelled advisory, omitted from Summary and uses a fallible GitHub jobs API query under `set -euo pipefail`. It has no tolerated-failure setting. The actual extracted script with a local `gh` failure exits1 before creating its summary (`design-evidence.json`). Full run success is required by release's `gate-ci-green`, snapshot admission and run collectors. Moreover `collect_readiness_runs.py:run_observation` records every CI job's conclusion and `validate_exact_head_readiness.exs:validate_run!` requires each applicable job to conclude success. Thus merely adding job-level `continue-on-error` can leave a failed job that still rejects READY. There is no existing advisory-job exemption in those authorities.

Prefer a step-level tolerated observation failure with an `id` and an always-run small renderer that reports `steps.<id>.outcome` as unavailable/failed observation, without invented zero timings. Preserve a successful observer job conclusion and all existing semantic jobs/whole-run gates; do not add a broad validation exemption. GitHub documents that step `continue-on-error` permits its job to pass and distinguishes pre-policy `outcome=failure` from post-policy `conclusion=success`. [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepscontinue-on-error), [steps context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#steps-context).

This is an aligned candidate, not a locally proven hosted one-line fix. Adverse acceptance must exercise actual workflow handling of observation API401/5xx/malformed data: raw observer outcome is failure, renderer says unavailable, observer job/semantic CI remain successful, and exact topology validator accepts that successful job inventory. Separately inject a semantic failure to prove Summary/full run/readiness/release remain red. Retain actual job/step outcomes; never relabel a failed test advisory. Job-level ignore or switching release to CI Summary alone is rejected because they conflict with complete topology proof or omit full-main semantic coverage.

The observer currently waits only for PR-critical jobs, so its main summary can see full-matrix/browser/Cohort jobs unfinished; it matches the obsolete prefix `Package Consumer Proof Matrix`, whereas the full job is named `Package Consumer Full Matrix + Release Preflight`. Fix reporting from the existing job IDs/names and explicitly mark partial observation. Do not silently claim its early table is full-main cost. A separate read-only post-run collector can obtain final attempts/timestamps without delaying semantic gates.

**5. Trim outer qualifier setup only after the large path is visible; preserve the native cold boundary.**

Prefer keeping fresh native qualification while replacing only the outer policy runtime with a small Jason/yamerl/Hex runtime after dependency audit; retain host libvips, PostgreSQL client, reviewed FFmpeg and browser OS prerequisites. Borrow the parser-only fixture idiom, not its fixture-only `mix` command interceptor or forced one-scheduler flags in native proof. A universal compiled build cache or sharing private qualification homes is rejected. Adverse acceptance: supported metadata, workflow topology, Hex and byte validator behave identically; corrupt parser/Hex payloads fail; arbitrary native Mix tasks cannot run through the outer adapter; fresh PLT, fresh package consumer and isolated signed registry still execute. Stop if a small runtime's maintenance/invalidation cost exceeds its measured gain. This is lower priority than the multi-hour path.
