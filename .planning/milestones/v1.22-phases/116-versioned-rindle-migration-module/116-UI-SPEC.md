## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline punctuation rhythm, code-label gaps if rendered styles are touched |
| sm | 8px | Short-list rhythm inside Markdown notes |
| md | 16px | Default paragraph, list, table, and fenced-code separation |
| lg | 24px | Spacing before `###` subsections and between grouped migration steps |
| xl | 32px | Spacing before `##` sections in rendered docs |
| 2xl | 48px | Major documentation transitions: install config -> migrations, migrations -> doctor verification, upgrade note -> legacy compatibility note |
| 3xl | 64px | Page-level top/bottom breathing room in rendered ExDoc pages only; do not simulate this in Markdown source |

Exceptions: Markdown source spacing is structural, not pixel-authored. Use one blank line before and after headings, paragraphs, lists, blockquotes, and fenced code blocks. Existing brand token `--rindle-space-3: 12px` may remain in generated admin CSS, but Phase 116 docs must not introduce new ad hoc spacing, inline HTML layout, or table-based layout hacks. Existing interactive target minimum remains 44px for admin UI, but this phase must not add admin controls.

Documentation rhythm rules:

- Keep the greenfield migration path compact: one short orientation paragraph, one migration module snippet, one Oban ownership note, one verification command.
- Do not nest the migration code snippet inside a numbered list item. Use a heading, paragraph, fenced code block, and short follow-up paragraph.
- Keep blockquotes to one short paragraph or one list of at most four bullets.
- Keep compatibility notes near the migration snippet; do not push legacy-adopter caveats into a distant troubleshooting section.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 17px | 400 | 1.6 |
| Label | 14px | 400 | 1.45 |
| Heading | 22px | 600 | 1.25 |
| Display | 30px | 600 | 1.15 |

Typography contract:

- Use exactly two weights in rendered docs surfaces: 400 regular and 600 semibold. Do not introduce 700-weight docs-specific headings in Phase 116.
- Markdown heading hierarchy must do the visual work: one page title, `##` for major reader jobs, then `###` for local subsections only.
- Keep prose measure to 68-78ch where a rendered docs surface exposes width control. Do not hard-wrap source lines solely to fake a measure.
- Use sentence case for new or changed headings: `Migrations`, `Run the Rindle migration`, `Oban ownership`, `Verification`, `Existing adopters`.
- Use `JetBrains Mono` only where rendered docs styling is available; in Markdown source, use backticks for module names, commands, file paths, versions, table names, and exact API names.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F7F4EA` warm-shell | Rendered documentation page background when Rindle styling is available |
| Secondary (30%) | `#FBFEFC` porcelain | Callout, table, and raised documentation surfaces when Rindle styling is available |
| Accent (10%) | `#123A35` deep-current | Migration-callout border, primary docs CTA/link emphasis, focus rings, and selected anchor emphasis only |
| Destructive | `#C83232` danger | Rollback/drop-table warnings around `Rindle.Migration.down/1` only |

Accent reserved for: the `Run the Rindle migration` callout border, a single primary docs CTA/link emphasis, focus rings in rendered docs, and selected anchor emphasis. Do not use accent color for every link, every heading, decorative dividers, or body text.

Color rules:

- GitHub and HexDocs may own final Markdown link colors; do not fight their renderer with inline HTML color.
- Rindle green `#32D08C` is a non-text accent on light surfaces because it fails body-text contrast there. Use it only as a non-text accent on dark/ink surfaces or leave it out.
- Status, warning, and destructive meaning must be paired with a visible label. Never rely on color alone.
- Do not use destructive red for normal upgrade friction. Reserve it for rollback/destructive copy tied to `down/1`.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Install Rindle tables |
| Empty state heading | No Rindle migration action is required |
| Empty state body | Your app already has Rindle's legacy packaged migrations applied. Keep those migrations in place, run `mix rindle.doctor`, and use the new `Rindle.Migration` module for fresh installs or future versioned upgrades. |
| Error state | Rindle migration status is unclear: run `mix rindle.doctor`, inspect the `doctor.migrations.pending` and `doctor.migrations.unresolved` checks, and keep existing migrations in place until the report is green. |
| Destructive confirmation | Roll back Rindle tables: Back up the database before running `Rindle.Migration.down/1`; it removes Rindle-owned tables only and does not manage `oban_jobs`. |

Required terminology:

| Term | Contract |
|------|----------|
| `Rindle.Migration.up/1` | Name as the public greenfield install path for Rindle-owned tables. |
| `Rindle.Migration.down/1` | Name as rollback-only/destructive; pair with backup language. |
| `Oban.Migration` | State that the host app owns Oban table installation. |
| `oban_jobs` | State that Rindle no longer creates or owns this shared table. |
| legacy packaged migrations | State that already-applied legacy migrations remain valid and should not be removed from adopter apps. |
| `mix rindle.doctor` | State as the post-migration verification command and the first troubleshooting step. |

Approved labels and callouts:

- `Migration:`
- `Oban ownership:`
- `Upgrade note:`
- `Rollback:`
- `Verification:`

Do not use custom admonition plugins. Use portable Markdown blockquotes with bold lead labels when a callout is needed.

## Migration Documentation UX Contract

| Surface | Required behavior | Source |
|---------|-------------------|--------|
| README `## Migrations` | Replace the raw `Application.app_dir(:rindle, "priv/repo/migrations")` + `Ecto.Migrator.run` install path with a compact adopter-owned migration module that calls `Rindle.Migration.up/1` and `Rindle.Migration.down/1`. | MIGRATE-01, ROADMAP Phase 116 |
| guides/getting_started.md `## 3. Run Host-App And Rindle Migrations Explicitly` | Rename or rewrite the step so the reader creates and runs a normal host-app migration using `Rindle.Migration`; keep the host Repo ownership and post-migration doctor verification. | MIGRATE-01 |
| guides/upgrading.md `## Unreleased / Next` | Add the Phase 116 migration note newest-first with `Applies to`, `What changed`, `Upgrade steps`, and `Verification`; explain fresh installs use `Rindle.Migration`, while existing legacy installs remain valid. | VERSION-02 carry-forward, MIGRATE-01 |
| Oban docs near install snippets | State that host apps install/manage Oban through `Oban.Migration`; Rindle must not create `oban_jobs` on the adopter's behalf. | MIGRATE-02 |
| doctor/runtime status docs | Preserve the existing reader path: run `mix rindle.doctor` after migrations; use runtime status for degraded work, not as the greenfield install CTA. | ROADMAP Phase 116 success criteria |
| tests/docs parity | Add or update proof so README, getting-started, and upgrading docs include the new migration module terms and reject the old raw packaged-migration greenfield path. | Existing docs parity pattern |

Reader journey:

1. The reader sees Repo and Oban ownership first: the adopter owns the Repo and the default Oban instance.
2. The first migration action is a normal host-app migration file that calls `Rindle.Migration.up/1` and `Rindle.Migration.down/1`.
3. The docs explicitly separate Rindle-owned tables from `oban_jobs`; `Oban.Migration` is the host app's responsibility.
4. The reader runs `mix ecto.migrate` through normal app workflow, then `mix rindle.doctor`.
5. Existing adopters are reassured that already-applied legacy packaged migrations remain valid and are not to be deleted.

Snippet rules:

- The final docs must show real implementation syntax, not placeholders like `<latest>` or `TODO`.
- If the implementation chooses a version option, the docs must use the actual latest supported version value or implementation-provided constant.
- Keep the displayed migration module to the minimum copyable shape: `use Ecto.Migration`, `def up`, `def down`.
- Do not show direct calls to private migration modules or instruct users to copy files from `priv/repo/migrations`.
- Do not introduce a public `mix rindle.*` install task in copy or examples.

Legacy compatibility copy:

- Use: `Existing apps that already applied Rindle's packaged migrations can leave them in place. The new module is the documented install path going forward; it does not require replaying or deleting legacy migration files.`
- Do not imply that existing adopters must rewrite migration history.
- Do not imply that Rindle owns host migrations, host Repo configuration, or Oban's shared jobs table.

## Interaction Contract

There is no browser UI interaction in this phase. The interactions are documentation-to-terminal workflows:

| Interaction | Contract |
|-------------|----------|
| Copy install snippet | The snippet must be copyable into a host Phoenix/Ecto migration file without hidden steps or HTML-only formatting. |
| Run migration | The next command should be the host app's normal migration workflow, such as `mix ecto.migrate`; do not invent a Rindle install task. |
| Verify setup | `mix rindle.doctor` is the primary verification action after migration. Error copy points to doctor migration checks first. |
| Rollback | `Rindle.Migration.down/1` is documented as rollback/destructive, paired with backup language and scoped to Rindle-owned tables. |
| Existing adopter decision | Existing adopters should be able to decide: leave legacy migrations alone, verify with doctor, and adopt the new module for future install/upgrade docs. |

No destructive UI confirmation modal is required because no UI is introduced. The confirmation approach is prose: label rollback as destructive, name the affected tables, require a backup, and say that `oban_jobs` is not managed by Rindle.
