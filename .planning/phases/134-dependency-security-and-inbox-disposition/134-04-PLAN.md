## Landing loop (defined once; Plan 05 iterates the same loop)

Queue entries carry: `number` (PR, assigned when created), `group`, `group_packages`, `lock` (mix.lock unless stated), `subject`. Each iteration runs L1 to L6 in order. Landings are serial; never pipeline.

- **L1 Prepare.** Maintainer lock-only entry not yet pushed: from a fresh `origin/main`, create branch `deps/<pkg>-advisory`, run `mix deps.update <pkg>` with the local toolchain env, require `git diff --name-only` to equal the lock file only, require `mix hex.audit` to no longer list that package's advisory ids, commit with the entry subject (without the PR number). Dependabot or own PR already open: nothing to build.
- **L2 Bring current.** Run `collect_inbox.sh` (read-only) and read the entry's PR record. If `behind` is true or the head predates the previous landing, the next checkpoint asks for the bring-current action: `@dependabot rebase` comment for Dependabot PRs (fallback `gh pr update-branch N --rebase` if Dependabot does not act within 15 minutes, which the user must authorize separately), `gh pr update-branch N --rebase` for maintainer and own PRs. New branches need push plus `gh pr create --base main` authorization instead.
- **L3 Current-head gate.** Watch the PR's checks read-only (`gh pr checks N --watch`, in the background). Re-run the collector and require for this PR: `behind` false, `ci_summary.conclusion` success on the current `head_sha`, and every `lock_delta` package in `group_packages` (the post-rebase delta, never the as-opened one). If the current-head CI is red, diagnose from the job log: a red caused by the bump changes the ledger disposition to `defer` with a gate and trigger (or `close`, which needs authorization) and the entry leaves the queue; any other red halts the iteration.
- **L4 Merge (user).** Update the ledger item's `head_sha` to the gated head and commit locally. At the checkpoint, show the exact command and let the user run it: `! gh pr merge N --squash --subject "<subject> (#N)"`.
- **L5 Post-merge evidence.** `git fetch origin main`, read the squash SHA from `gh pr view N --json mergeCommit`, confirm it is on origin/main, wait for its ci.yml push run, then run `dep_landing_evidence.sh --sha <squash> --group <group> --packages <csv> --lock <lock> --baseline-sha <previous landing or baseline sha> --out <scratch>`. Exit 75 means poll again; exit 0 credits; exit 1 (regression or attribution failure) halts and the next checkpoint asks for an authorized single-commit revert PR (`git revert <squash>`, subject `revert: <subject>`); exit 3 (inherited red) halts and the next checkpoint asks for `gh run rerun <id> --failed`, then L5 repeats once.
- **L6 Record.** Append the evidence as a `landings[]` record (number, group, group_packages, lock, merge_sha, ci_run_id, baseline_run_id, lock_delta, gates, subject), set the item's `terminal` to `{state: "closed", merged: true}`, mark advisories whose ids are now absent from a fresh `mix hex.audit` as `resolved`, run `validate_inbox_ledger.sh --offline`, and commit `docs(phase-134): record <group> landing`. Read `gh pr list --label "autorelease: pending" --state open --json number,title` and halt if a release PR appeared because of this landing (D-134-08).

Halt rule (D-134-01): the second halt on the same gate for the same entry stops the plan for rescoping; no extra plans are added inside this phase.
