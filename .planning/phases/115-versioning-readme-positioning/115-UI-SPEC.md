# Phase 115 - UI Design Contract

> Visual and interaction contract for README and documentation UX. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none - Phase 115 is Markdown/ExDoc documentation positioning, not an app screen. Do not initialize shadcn. Source: phase context, RESEARCH.md |
| Preset | not applicable |
| Component library | none for this phase; do not add Radix, shadcn, Tailwind UI, daisyUI, or registry blocks. Existing docs render through GitHub Markdown and ExDoc extras. Source: RESEARCH.md, guides/ui_principles.md |
| Icon library | none; use text labels and Markdown headings, not decorative icons. |
| Font | GitHub/HexDocs renderer default for README source. If a rendered Rindle docs surface is styled, use brand tokens: Atkinson Hyperlegible for body, Space Grotesk for headings, JetBrains Mono for code. Source: brandbook/tokens/tokens.json |

Implementation boundary: this contract governs information hierarchy, Markdown structure, copy, callouts, and rendered-doc token choices. It does not authorize new CSS, JS, or component dependencies. If executor touches generated docs styling anyway, it must use `brandbook/tokens/tokens.json` and generated `--rindle-` custom properties only.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline punctuation rhythm, callout label-to-copy gap if rendered styles are touched |
| sm | 8px | List item rhythm inside short Markdown callouts |
| md | 16px | Default paragraph, list, table, and fenced-code separation |
| lg | 24px | Spacing before `###` subsections and between grouped setup steps |
| xl | 32px | Spacing before `##` sections in rendered docs |
| 2xl | 48px | Major README transitions: intro -> first attachment, first attachment -> deeper runtime setup, AV quickstart -> next reads |
| 3xl | 64px | Page-level top/bottom breathing room in rendered ExDoc pages only; do not simulate this in Markdown source |

Exceptions: Markdown source spacing is structural, not pixel-authored. Use one blank line before and after headings, paragraphs, lists, tables, blockquotes, and fenced code blocks. Existing brand token `--rindle-space-3: 12px` may remain in generated admin CSS, but Phase 115 README/guide edits must not introduce new ad hoc spacing or HTML-only layout hacks.

Documentation rhythm rules:

- Keep the first-run path as a compact vertical sequence: intro paragraph, profile snippet, facade call flow, short dependency note, next read.
- Do not place long prerequisite matrices in the first-run path. Link to `Running` for FFmpeg/libvips matrices.
- Keep callouts to one short paragraph or one list of at most five bullets.
- Code examples must be separated from surrounding prose by one blank line and must not be nested inside list items unless the list is the interaction sequence.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 17px | 400 | 1.6 |
| Label | 14px | 400 | 1.45 |
| Heading | 22px | 600 | 1.25 |
| Display | 30px | 600 | 1.15 |

Typography contract:

- Use exactly two weights in rendered docs surfaces: 400 regular and 600 semibold. Do not introduce 700-weight docs-specific headings in Phase 115.
- Markdown heading hierarchy must do the visual work: one `# Rindle`, then `##` for major reader jobs, then `###` for local subsections only.
- Keep prose measure to 68-78ch where a rendered docs surface exposes width control. Do not hard-wrap source lines solely to fake a measure.
- Use sentence case for headings: "Versioning and stability", "First Attachment in ~2 Minutes", "When Not to Use Rindle".
- Use `JetBrains Mono` only where rendered docs styling is available; in Markdown source, use backticks for module names, commands, file paths, versions, and exact API names.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F7F4EA` warm-shell | Rendered documentation page background when Rindle styling is available |
| Secondary (30%) | `#FBFEFC` porcelain | Callout, table, and raised documentation surfaces when Rindle styling is available |
| Accent (10%) | `#123A35` deep-current | Versioning callout border, first-attachment CTA emphasis, focus rings, and selected anchor emphasis only |
| Destructive | `#C83232` danger | Destructive or data-loss warnings only; Phase 115 has no destructive action |

Accent reserved for: `Versioning and stability` callout border, the first-run CTA/link emphasis, focus rings in rendered docs, and package/version affordances. Do not use accent color for every link, every heading, decorative dividers, or body text.

Color rules:

- GitHub and HexDocs may own final Markdown link colors; do not fight their renderer with inline HTML color.
- Rindle green `#32D08C` is a non-text accent on light surfaces because it fails body-text contrast there. Use it only as a non-text accent on dark/ink surfaces or leave it out.
- Status or warning color must be paired with a visible label. Never rely on color alone.
- Do not introduce destructive red for "when not to use" positioning; that section is a product-fit boundary, not an error state.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Create first attachment |
| Empty state heading | No upgrade notes for this version yet |
| Empty state body | There are no adopter action items for this version. Review `CHANGELOG.md` before upgrading, then return here when a release lists migration or behavior changes. |
| Error state | First attachment failed: run `mix rindle.doctor`, verify storage credentials, and keep the path original-only until the base upload lifecycle works. Install libvips before image variants/background image processing and FFmpeg before AV work. |
| Destructive confirmation | None - Phase 115 introduces no destructive actions and no confirmation UI. |

Required README heading and label contract:

| Surface | Required copy | Placement |
|---------|---------------|-----------|
| README | `## Versioning and stability` | Above first-run code, near install/orientation |
| README | `## First Attachment in ~2 Minutes` | First hands-on path; must appear before any AV quickstart heading, FFmpeg prerequisite, libvips prerequisite, `kind: :video`, or `Rindle.Profile.Presets.Web` |
| README | `## AV Quickstart` | Below the image/original-only first attachment path; clearly framed as the heavier path |
| README | `## When Not to Use Rindle` | Before final guide links or near positioning section; lift and compress from `guides/user_flows.md` |
| CONTRIBUTING | `## Versioning and stability` | Near the top, before CI/release-process detail |
| guides/upgrading.md | `## Version index` | Immediately after the intro |
| guides/upgrading.md | `## Unreleased / Next` | First entry in the versioned notes |
| guides/upgrading.md | `## 0.1.3 and earlier -> current AV-aware runtime` | Preserve the current pre-0.1.4 upgrade path as a versioned section |

README interaction hierarchy:

1. Logo, badges, one-sentence value proposition, and the "narrow quickstart" orientation stay at the top.
2. The first actionable path is original-only image attachment, expressed as `Create first attachment` and a five-call facade flow.
3. The first-run path must use an image profile with `variants: []`, `allow_mime`, and `max_bytes`.
4. The first-run path must not imply that background image processing is libvips-free. The safe claim is: the original-only first attachment avoids AV setup and does not require FFmpeg; image variants/background processing still need libvips.
5. AV setup is a secondary path below the first attachment. It may mention `FFmpeg >= 6.0`, `Rindle.Profile.Presets.Web`, `web_720p`, and poster variants only after the image-first path.
6. The "when not to use" block must make self-disqualification easy: Rindle is a Phoenix/Ecto library, not a hosted media platform, CDN replacement, DRM system, full streaming platform, AI/GPU processing suite, or broad document-processing system.

Callout treatment:

- Use portable Markdown blockquotes with bold lead labels, not custom admonition plugins.
- Approved labels: `Versioning:`, `Note:`, `When not to use Rindle:`, `Upgrade note:`.
- Maximum three callouts before `AV Quickstart`.
- Keep callouts factual and short. No marketing claims, hype, or decorative language.
- Do not use warning/error styling for normal versioning or product-fit boundaries.

Upgrade/versioning affordances:

- README and CONTRIBUTING must use the same stability sentence: `Rindle follows Semantic Versioning. While Rindle is 0.x, public APIs may change between minor versions; review CHANGELOG.md and guides/upgrading.md before upgrading. Rindle 1.0 will mean the public API is stable enough that breaking public API changes move to major versions.`
- `guides/upgrading.md` must separate "what changed" from "what to do" using these exact subsection labels under each version: `Applies to`, `What changed`, `Upgrade steps`, `Verification`.
- The upgrade guide must be newest-first and link to `CHANGELOG.md`.
- Do not document future `Rindle.Migration.up/1` or `down/1` in Phase 115. Phase 116 owns that API.
